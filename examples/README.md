# Examples

## YAML job and state data

[fit.yaml](../examples/fit.yaml) contains the configuration. Its `input.path` points to [states.csv](../examples/states.csv), resolved relative to the YAML file even when the command runs from another directory. The CSV contains 61 synthetic TEME position/velocity samples, spaced two minutes apart from `2026-01-01T00:00:00Z` through `2026-01-01T02:00:00Z`.

From the repository root, after building:

```sh
build/release/orbit-fit fit --config examples/fit.yaml --output-dir results
```

The configuration declares the following input:

```yaml
input:
  path: states.csv
  format: csv
  frame: TEME
  time_system: UTC
  position_unit: m
  velocity_unit: m/s
```

The CSV header is `epoch,x,y,z,vx,vy,vz`. Each row holds a UTC timestamp and six numeric values in the declared units. Position units may also be `km`, and velocity units `km/s`. Both state vectors are required. Comment lines begin with `#`; the [input contract](../docs/input.md) gives the exact syntax and limits.

| YAML field | Purpose |
|---|---|
| `schema` | Selects `orbit-fit.job.v1` |
| `input` | Names the state file and explicitly declares its format, frame, time system, and units |
| `metadata` | Identifies the object in TLE/OMM products |
| `fit.start`, `fit.stop` | Select the inclusive fitting window |
| `fit.epoch` | Sets the fitted mean-element epoch |
| `fit.maximum_rms_position_m` | Sets the physical acceptance threshold in metres |
| `seed_omm` | Optional path to an OMM JSON seed at the requested epoch |

Catalog number `99999` and object name `SYNTHETIC EXAMPLE` identify synthetic data; replace them with the actual object's identity for real input. This example uses automatic initialization, fixed BSTAR, and approximation weights. It requires a position RMS of at most 10 m for the continuous fit and both reparsed products.

The output directory must not exist. A successful fit exits with code 0 and writes `elements.tle`, `elements.omm.json`, `report.json`, the unchanged input as `input.yaml` and `states.csv`, and a resolved SI `request.json`. The snapshot embeds every state and any seed, so it can be replayed after the original files move:

```sh
build/release/orbit-fit fit --input results/request.json --output-dir replay
```

Generate a new pair of example files in a new directory:

```sh
build/release/orbit-fit example --output-dir example
build/release/orbit-fit fit --config example/fit.yaml --output-dir example-results
```

The fixtures were generated by watson using the native C++ example command and the unmodified Vallado propagation path. They are runnable format/integration examples, not independent tracking data.

## Compatible inline JSON input

[request.json](../examples/request.json) contains the same example as a self-contained `orbit-fit.request.v1` document. It remains useful for programmatic callers and requests with per-sample covariance. JSON does not permit comments, so its description and authorship live here.

```sh
build/release/orbit-fit fit --input examples/request.json --output-dir json-results
build/release/orbit-fit example --output request.json
```

Supply exactly one of `--config` and `--input`. The CLI tests compare delivered products and reports from the YAML/CSV and equivalent JSON inputs.

## C++ API examples

- [fit.cpp](../examples/fit.cpp): synthetic fitting and shared product validation.
- [forecast.cpp](../examples/forecast.cpp): fitting the frozen NASA ISS forecast and checking held-out predictions.
- [cancellation.cpp](../examples/cancellation.cpp): cooperative cancellation and result handling.

The C++ examples compile and run under CTest. The forecast example has its own fixture reader with unit-bearing CSV column names; use the header documented above for the CLI.
